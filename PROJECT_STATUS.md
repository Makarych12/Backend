## О проекте

Интерактивный обучающий веб-сайт (SPA на React) — курс программирования **с абсолютного нуля**
до написания настоящих backend-серверов на Python (FastAPI).

**Аудитория:** полный новичок в программировании. Максимум знаний на старте — поверхностные
HTML/CSS. Ученик никогда не видел терминал, не устанавливал Python, не знает, что такое
переменная. Курс ведёт за руку с первого модуля ("что такое код") до архитектуры настоящих
API-серверов.

**Цель курса:** довести ученика до уровня, на котором он может пройти техническое собеседование
на позицию junior/middle backend-разработчика на Python, имея готовое портфолио из 4 проектов
(см. раздел "Итоговые проекты" ниже).

**Важное свойство продукта:** это не просто текст со скриншотами кода — Python в уроках
**реально выполняется прямо в браузере** (через Pyodide/WebAssembly), включая мини-реализацию
FastAPI/Pydantic/SQLAlchemy, так что ученик пишет и запускает настоящий код с первого дня, без
установки чего-либо на свой компьютер.

## Формат обучения — ОБЯЗАТЕЛЬНО К СОБЛЮДЕНИЮ

Все 9 готовых модулей строго следуют одному формату. **Не изобретай новый формат** — открой
готовый файл-образец и копируй структуру:

- **Эталонный файл:** `src/data/modules/module8.js`, урок `oauth2-fastapi` (последний урок файла) —
  самый полный пример, использует все типы блоков сразу.
- **Исторически первый образец, с которого формат пошёл:** `src/data/modules/module5.js`, урок

### Стиль объяснений

- Максимально просто, как ребёнку: короткие предложения, без непояснённого жаргона.
- Каждый новый термин при первом употреблении получает бытовую аналогию (см. `type: 'analogy'`
  ниже) — трафарет для Pydantic, охранник на входе для аутентификации, мясорубка для хеширования,
  браслет на фестивале для JWT и т.д. Это не украшение, а обязательный элемент почти каждого урока.
- Никогда не считай что-то "очевидным". Если вводишь `Depends`, `Header`, `HTTPException` —
  объясни, что это и зачем, даже если это уже третий раз в курсе (можно короче, но не молча).

### Структура одного урока (объект внутри `lessons: [...]`)

Каждый урок — это объект со следующими полями (не все обязательны — см. пометки):

```js
{
  id: 'kebab-case-unique-id',      // уникален ВО ВСЁМ КУРСЕ, не только в модуле
  title: '...',
  summary: '...',                   // одна строка под заголовком урока
  theory: [ /* массив блоков, см. ниже */ ],
  example: { title, lang, code, explanation },       // необязательно, но почти всегда есть
  terminal: { title, description, script: [...] },    // только если в уроке нужны команды
  sandbox: { bootstrap, description, initialCode },   // см. раздел про песочницу ниже
  tasks: [ { title, difficulty, description, hints: [...], solution? }, ... ], // 2-3 штуки
  mistakes: [ { wrong, right }, ... ],                 // обычно 2
  checklist: [ 'строка', 'строка', ... ],               // обязателен всегда, ~4-5 пунктов
}
```

`theory` — массив блоков, рендерится компонентом `TheoryBlock` в `src/pages/LessonPage.jsx`.
Доступные `type` (используй только их, другие не отрендерятся):

- `{ type: 'p', text }` — обычный абзац
- `{ type: 'analogy', text }` — блок "Представь так" (бытовая аналогия)
- `{ type: 'callout', variant: 'info'|'warning', title, text }` — врезка с акцентом
- `{ type: 'command', command, parts: [{text, desc}], result }` — разбор терминальной команды по частям
- `{ type: 'steps', title, items: [{code, note}] }` — пошаговая сборка примера кода "по кусочкам"
- `{ type: 'list', title, items: ['строка', ...] }` — маркированный список
- `{ type: 'terminal', title, script }` — терминал прямо внутри теории (редко нужен, обычно
  используется отдельное поле `lesson.terminal`)

`tasks[].difficulty` — строго одно из `'easy' | 'medium' | 'hard'`, по возрастанию сложности,
обычно ровно 3 задания. `hints` — массив строк, кликабельно раскрываются по одной
(компонент `Hint.jsx`). `solution` необязателен — добавляй его для заданий, где полезно
показать готовый код (не для всех заданий подряд).

### Песочница (`sandbox`) — САМОЕ ВАЖНОЕ ПРАВИЛО ЭТОГО ПРОЕКТА

`sandbox.initialCode` — это НАСТОЯЩИЙ Python, который выполняется в браузере ученика через
Pyodide (WebAssembly CPython), не имитация и не текст-картинка. `sandbox.bootstrap` определяет,
какой "мини-движок" подставляется в `sys.modules` ДО кода ученика (см. `pyodideRunner.js` →
`BOOTSTRAP_SOURCE` / `BOOTSTRAP_PACKAGES`):

- `bootstrap: null` (или поле не указано) — чистый Python, только стандартная библиотека
  (`hashlib`, `hmac`, `secrets`, `base64`, `json` и т.д. — работают из коробки, без загрузки)
- `bootstrap: 'fastapi'` — подставляет `src/utils/miniFastapi.py`: рабочие `FastAPI`, `BaseModel`,
  `Field` (с `gt/ge/lt/le/min_length/max_length`), `HTTPException`, `ValidationError`,
  `Depends`, `Header`, `fastapi.security.OAuth2PasswordBearer`/`OAuth2PasswordRequestForm`,
  `fastapi.status`, `fastapi.testclient.TestClient` (поддерживает `headers=` и `data=` для form-data)
- `bootstrap: 'sqlalchemy'` — подставляет `src/utils/miniSqlalchemy.py` (мини-ORM, см. ниже) и
  ДОГРУЖАЕТ настоящий пакет `sqlite3` для Pyodide (он не встроен в Pyodide по умолчанию,
  в отличие от обычного CPython — `pyodideRunner.js` вызывает `pyodide.loadPackage('sqlite3')`)
- `bootstrap: 'sqlite3'` — только догружает настоящий модуль `sqlite3`, без подмены модулей —
  используется, когда урок учит SQL напрямую, без ORM

**Обе мини-реализации (`miniFastapi.py`, `miniSqlalchemy.py`) написаны так, что код ученика
выглядит и пишется один в один как настоящая библиотека** (`from fastapi import FastAPI`,
`from sqlalchemy.orm import declarative_base`) — ученик не должен ощущать, что это подделка.

**КРИТИЧЕСКИ ВАЖНАЯ ДЕТАЛЬ ДИЗАЙНА мини-движков:** весь код внутри `miniFastapi.py` и
`miniSqlalchemy.py` обёрнут в одну функцию `_bootstrap()`, которая вызывается в конце файла и
сразу удаляется (`_bootstrap(); del _bootstrap`). Это **обязательно** для любого нового
мини-движка, который будешь добавлять (например, для WebSockets в проекте 4 или Celery/Redis
в модуле 14). Причина: bootstrap-код и код ученика выполняются В ОДНОМ И ТОМ ЖЕ пространстве
имён Pyodide (`namespace` в `pyodideRunner.js`). Если определить класс `Session` на верхнем
уровне файла (а не внутри `_bootstrap()`), то стандартная для SQLAlchemy строчка ученика
`Session = sessionmaker(bind=engine)` молча ЗАТРЁТ внутренний класс с тем же именем — и всё
сломается труднообъяснимой ошибкой. Это реальный баг, найденный и исправленный при разработке
модуля 7 — не повтори его в новом мини-движке.

**КАК ВАЛИДИРОВАТЬ ПЕСОЧНИЦЫ ПЕРЕД ТЕМ, КАК СЧИТАТЬ УРОК ГОТОВЫМ** (обязательный шаг, не
пропускай): в этом проекте нет браузера, доступного агенту напрямую, зато есть Node.js c npm-пакетом
`pyodide` — им запускался КАЖДЫЙ `sandbox.initialCode` во всех 9 готовых модулях перед сдачей.
Рецепт (выполнять во временной scratch-папке, не в самом проекте):

```bash
mkdir /tmp/pyodide-check && cd /tmp/pyodide-check
npm init -y && npm install pyodide@0.26.4
```

```js
// check.mjs
import { loadPyodide } from "pyodide";
import { readFileSync } from "fs";

const MINI = readFileSync("/path/to/src/utils/miniFastapi.py", "utf8"); // или miniSqlalchemy.py
const pyodide = await loadPyodide();
// если нужен sqlite3: await pyodide.loadPackage("sqlite3");
const ns = pyodide.globals.get("dict")();
pyodide.setStdout({ batched: (t) => console.log(t) });
pyodide.setStderr({ batched: (t) => console.log("ERR:", t) });
await pyodide.runPythonAsync(MINI, { globals: ns });          // bootstrap, если он есть
await pyodide.runPythonAsync(`ТУТ sandbox.initialCode`, { globals: ns });
```

Прогони буквально ТОТ ЖЕ текст, что лежит в `sandbox.initialCode` в файле модуля (лучше всего —
скриптом, который импортирует `moduleN.js` через `import()` и прогоняет `lesson.sandbox` каждого
урока по очереди). Если хоть один урок падает с исключением — урок не готов. Не сдавай модуль,
не прогнав через это все его песочницы. После проверки удали `node_modules` из scratch-папки —
он тяжёлый и не нужен в самом репозитории.

### Терминал (`terminal`)

Используется, когда в уроке есть команды, которые нельзя (или не нужно) реально выполнять —
`pip install`, `uvicorn ...`, `alembic ...` и т.д. Два режима:

- **Свободный ввод** (`lessonCommands`, `suggestions`) — ученик сам печатает команды, ответ
  генерирует `src/utils/terminalSimulator.js` (реалистичный вывод `pip install`, `pip list`,
  `python --version`, активация venv и т.д. — уже поддерживает пакеты `fastapi`, `uvicorn`,
  `sqlalchemy`, `alembic`, `psycopg2-binary`, `python-dotenv`, `pytest`, `httpx`, `passlib`,
  `bcrypt`, `python-jose`, `celery`, `redis`, `websockets`, `requests`, `jinja2`,
  `python-multipart` — список версий в объекте `PACKAGES` в этом файле, дополняй его при
  необходимости для новых модулей)
- **Пошаговый сценарий** (`script: [{ command, output?, type? }]`) — ученик жмёт "Дальше",
  команды выполняются по порядку. Если `output` не задан — берётся реалистичный вывод из
  симулятора (для `pip install`, `uvicorn`); если задан — используется дословно (нужно для команд,
  которые симулятор не знает, например `alembic ...` или гипотетический `python check.py`)

## Что нужно сделать дальше — КОНКРЕТНО

Пользователь просит модули пачками (например, "продолжай, модули 10-13") — **не делай все
оставшиеся 6 модулей за один присест без явной просьбы**, это отдельно проверенное правило
работы над этим проектом (агент до тебя уже поймал эту обратную связь один раз). Делай ровно
те модули, которые явно назвали, добавляя каждый новый lesson-файл + импорт и запись в массив
`modules` в `src/data/modules/index.js` (удаляя соответствующий `stub(...)`), остальное оставляй
как есть.

Для каждого модуля ниже — 3-4 урока (столько же, сколько в готовых модулях 5-9), формат —
строго как описано в разделе "Формат обучения" выше, включая обязательную валидацию каждой
песочницы через Node+Pyodide перед тем, как считать модуль готовым.

### Модуль 10 — Тестирование (`testing`, order 10, иконка 🧪)

- **Зачем нужны автотесты** — аналогия (например: тест как "контрольный список перед вылетом
  самолёта" — проверяешь по чек-листу автоматически, а не полагаешься на память и удачу).
  Разница между "я протестировал руками один раз" и "тест запускается сам при каждом изменении
  кода".
- **pytest с нуля**: установка (`pip install pytest`), структура `test_*.py`, функции `def
  test_...():`, `assert`, что происходит при падении теста (понятный diff), запуск `pytest`
  и `pytest -v` в терминале (`terminalSimulator.js` уже знает пакет `pytest`, добавь при
  необходимости реалистичный вывод запуска — как ответ на команду `pytest` сейчас его нет,
  добавь через `lessonCommands`/`script.output`, либо расширь сам симулятор).
- **Фикстуры (`@pytest.fixture`)**: переиспользуемые "заготовки" для тестов (например, тестовый
  клиент, тестовая база данных) — аналогия "одна и та же сервировка стола перед каждым блюдом".
- **TestClient — уже знаком с модуля 5**, но здесь — по-настоящему как инструмент тестирования
  (а не просто способ обойти отсутствие сети в браузере): `assert response.status_code == 200`,
  `assert response.json() == {...}`, тестирование happy path И ошибок (404, 422) для одного роута.
- **Тестирование с базой данных**: изолированная тестовая БД (например, отдельный
  `sqlite:///:memory:` на каждый тест — обрати внимание, это ровно то же самое, что уже
  используется в песочницах модуля 7, так что можно опираться на уже знакомый ученику паттерн),
  почему нельзя тестировать на настоящей продакшен-базе.
- Для песочниц этого модуля используй `bootstrap: 'fastapi'` (роуты для тестирования) и, где
  нужно, `bootstrap: 'sqlalchemy'`. Настоящего `pytest` в Pyodide нет и ставить не нужно — пиши
  функции `test_...()` и вызывай их вручную с `assert` внутри `initialCode` (сам `assert` —
  всегда доступен, это ключевое слово Python, не библиотека), поясни ученику, что на его
  компьютере эти же функции запустит сама команда `pytest`, автоматически найдя их по имени.

### Модуль 11 — Безопасность (`security`, order 11, иконка 🛡️)

- **CORS**: что это и почему браузер блокирует запросы с другого домена по умолчанию (аналогия
  "список гостей на входе" — сервер сам решает, каким сайтам разрешено обращаться к нему из
  браузера). Заголовки `Access-Control-Allow-Origin`, настройка `CORSMiddleware` в FastAPI
  (`from fastapi.middleware.cors import CORSMiddleware`) — потребуется добавить поддержку
  `add_middleware` в `miniFastapi.py`, если хочешь дать это реально запускаемым кодом; если не
  успеваешь — можно оформить как некликаемый пример (`example`, без `sandbox`) с честной пометкой,
  что миддлвари в мини-движке пока не поддержаны.
- **SQL-инъекции**: подробно уже введено в модуле 7 (урок `what-is-database`, задание 3) —
  здесь нужно углубить: показать инъекцию не только в SELECT, но и в других местах (например,
  в ORDER BY, если имя столбца собирается из пользовательского ввода), объяснить, почему
  ORM (SQLAlchemy) сам по себе не является 100% защитой, если использовать "сырые" строки
  (`text()` с f-строкой) вместо параметров даже внутри ORM-кода.
- **Rate limiting**: зачем ограничивать количество запросов с одного адреса (аналогия "один
  посетитель — не больше N звонков в отдел поддержки за минуту, иначе кладём трубку") — защита
  от перебора паролей и от перегрузки сервера. Концептуально + пример кода со счётчиком в
  словаре (можно реализовать по-настоящему на чистом Python внутри `bootstrap: 'fastapi'`
  роута — засеки время последнего запроса на IP в словаре, откажи, если слишком часто).
- **Переменные окружения**: почему пароли/ключи/токены (включая `SECRET_KEY` из модуля 8!)
  нельзя хранить прямо в коде, который попадает в git — `.env` файл, `python-dotenv`
  (`from dotenv import load_dotenv`), `os.getenv("SECRET_KEY")`, `.gitignore`. `os.getenv` —
  реальная стандартная библиотека, доступна в песочнице без бутстрапа; `.env`-файл в браузере
  прочитать неоткуда, поэтому это — пример через `terminal`/`example`, а в песочнице показывай
  `os.environ["SECRET_KEY"] = "..."` как имитацию того, что переменная уже установлена окружением.
- Свяжи этот модуль явно с уже пройденным: "помнишь SECRET_KEY из модуля 8? Вот куда его
  на самом деле следовало положить".

### Модуль 12 — Асинхронность (`async`, order 12, иконка ⚡)

- **Зачем вообще async именно в FastAPI**: аналогия повара, который, пока варится суп (I/O —
  ожидание ответа от базы данных или другого сервера), не стоит истуканом у плиты, а успевает
  нарезать салат для следующего заказа — вместо того чтобы КАЖДЫЙ заказ ждать по очереди.
  Разница между CPU-bound (расчёты — async не поможет) и I/O-bound (ожидание сети/диска —
  именно здесь async даёт выигрыш) работой.
- **`async def` / `await` на простых примерах** без FastAPI сначала (`asyncio.sleep(1)` вместо
  `time.sleep(1)`, показать разницу во времени при параллельных вызовах через `asyncio.gather`).
- **`async def` роуты в FastAPI**: `@app.get("/") \n async def root(): ...`, когда использовать
  `async def`, а когда обычный `def` тоже нормально (FastAPI сам выполняет обычные `def`-роуты
  в отдельном потоке, чтобы не блокировать остальных — это стоит объяснить явно, частый
  вопрос на собеседовании).
- **Частая ошибка**: вызвать блокирующую синхронную операцию (например, `time.sleep()` или
  синхронный запрос к базе) ВНУТРИ `async def` — это блокирует вообще все остальные запросы
  сервера, а не только текущий. Обязательно разбери как "типичная ошибка новичка" с конкретным
  примером до/после.
- **ВАЖНЫЙ ТЕХНИЧЕСКИЙ МОМЕНТ ДЛЯ ЭТОГО МОДУЛЯ**: `miniFastapi.py` сейчас поддерживает ТОЛЬКО
  синхронные `def`-роуты и `def`-зависимости — `TestClient._call` вызывает `route.func(**kwargs)`
  напрямую, без `await`/`asyncio.run`. Чтобы дать ученику реально запускаемый `async def`-пример
  в песочнице, тебе нужно будет расширить `_resolve_kwargs`/`_call`/`Depends`-резолвер в
  `miniFastapi.py`, чтобы: 1) проверять `inspect.iscoroutinefunction(route.func)` и, если да,
  выполнять через `await route.func(**kwargs)` (сам `_call` при этом должен стать `async def`,
  а `TestClient.get/post/...` — тоже `async def`, что потребует от ученика писать `await
  client.get(...)` в песочнице — это, кстати, соответствует тому, как по-настоящему устроен
  `httpx.AsyncClient` в реальных проектах, так что это не искажение, а более честная картина);
  2) аналогично поддержать `async def`-зависимости в `Depends(...)`. Проверь после этого
  изменения ВСЕ старые песочницы модулей 5-11 (`bootstrap: 'fastapi'`) — они по-прежнему должны
  работать без единой правки, так как остаются полностью синхронными.

### Модуль 13 — Деплой (`deploy`, order 13, иконка 🚀)

- **Зачем нужен Docker**: аналогия контейнеровоза — стандартный контейнер помещается на любой
  корабль/поезд/грузовик одинаково, неважно, что внутри. Docker-контейнер точно так же "упаковывает"
  твоё приложение со всем окружением (версия Python, все библиотеки), чтобы оно одинаково
  работало и у тебя на компьютере, и на сервере ("работает у меня" перестаёт быть проблемой).
- **`Dockerfile` с нуля**: `FROM python:3.12-slim`, `WORKDIR /app`, `COPY requirements.txt .`,
  `RUN pip install -r requirements.txt`, `COPY . .`, `CMD ["uvicorn", "main:app", "--host",
  "0.0.0.0", "--port", "8000"]` — разбери каждую строчку через блок `type: 'command'`/`'steps'`,
  как уже делалось для `pip install fastapi uvicorn` в модуле 5.
  - **Реалистичный terminal-сценарий**: `docker build -t myapp .`, `docker run -p 8000:8000
    myapp` — симулятор команд (`terminalSimulator.js`) пока НЕ знает команду `docker` вообще
    (упадёт в `bash: docker: command not found`) — добавь обработку `docker build`/`docker run`
    туда же, где обрабатываются `pip`/`uvicorn`, с реалистичным логом сборки слоёв.
- **`docker-compose.yml`**: запуск приложения И базы данных (PostgreSQL из модуля 7) вместе одной
  командой `docker compose up` — аналогия "пульт с несколькими кнопками включает сразу весь
  оркестр инструментов, а не каждый по отдельности".
- **Деплой на Render/Railway**: пошагово, как реальный процесс (это будет практически весь урок
  в виде `terminal`/`steps`, не сандбокс — реальный деплой на внешний сервис в браузере ученика
  не воспроизвести): подключение git-репозитория, переменные окружения в панели сервиса (прямая
  отсылка к модулю 11 — "вот куда на самом деле кладётся `.env` в проде"), что такое build-команда
  и start-команда у сервиса.
- У этого модуля почти нет реальных `sandbox`-блоков (Docker и деплой нельзя выполнить в
  браузере) — это нормально, опирайся на `terminal` (пошаговые сценарии) и `example`/`steps`
  для теории, как уже сделано в модуле 7 для урока про Alembic (`alembic-migrations` в
  `module7.js` — там вообще нет `sandbox`, только `terminal` и `tasks` на рассуждение).

### Модуль 14 — Продвинутый backend (`advanced`, order 14, иконка 🧠)

- **Очереди задач (Celery + Redis)**: зачем откладывать долгую работу "на потом" вместо того,
  чтобы заставлять клиента ждать прямо во время HTTP-запроса (аналогия: не заставлять посетителя
  стоять у кассы, пока готовится сложный заказ — выдать ему номерок и отпустить, уведомить,
  когда будет готово). `@app.task`, `.delay(...)`, воркер как отдельный процесс.
- **Кэширование (Redis)**: зачем хранить результат дорогого вычисления/запроса, чтобы не
  повторять его для каждого одинакового запроса (аналогия шпаргалки: один раз посчитал ответ —
  записал, в следующий раз просто подсмотрел). TTL (время жизни кэша), инвалидация кэша
  ("самая сложная задача в программировании" — можно даже так и написать как шутку-факт).
- **WebSockets в FastAPI**: `@app.websocket("/ws")`, `await websocket.accept()`,
  `await websocket.receive_text()`/`send_text()`, разница с обычным HTTP-запросом (постоянное
  соединение вместо "спросил-ответили-закрыли"). **Это прямая теоретическая база для итогового
  проекта 4 (чат, см. ниже)** — обязательно свяжи явно.
- **ТЕХНИЧЕСКИЙ МОМЕНТ**: ни Celery, ни Redis, ни настоящие WebSocket-соединения нельзя
  по-настоящему запустить в браузерной песочнице (нужны отдельные процессы/реальная сеть).
  Для Celery/Redis — используй `terminal` (симулятор уже знает пакеты `celery`, `redis` для
  `pip install`) + `example` без `sandbox`, честно указывая это ограничение в описании, как уже
  сделано для PostgreSQL в модуле 7 (`postgres-connection`) и для Alembic. Для WebSockets можно
  попробовать написать МИНИ-реализацию `websocket`-эндпоинтов в `miniFastapi.py` (по аналогии с
  тем, как сделаны `Depends`/`Header`) с фейковым "клиентом", который кладёт/забирает сообщения
  из `list` в памяти — если это кажется слишком сложным на момент разработки, честный `example`
  без `sandbox` тоже приемлем (так же, как для Alembic), но постарайся сначала оценить, не займёт
  ли мини-реализация меньше времени, чем кажется — по духу проекта тут предпочтителен реально
  работающий код, а не просто текст.

## Известные проблемы / на что обратить внимание

- **Мини-движки не поддерживают `async def`** нигде (роуты, зависимости) — только синхронные
  функции. Это осознанное упрощение ДО модуля 12 — в модуле 12 его придётся снять (см. подробности
  выше в описании модуля 12). После этого изменения обязательно перепроверь все существующие
  песочницы модулей 5-11 (`bootstrap: 'fastapi'`) на регресс.
- **`Depends(...)` в `miniFastapi.py` не кэшируется в рамках одного запроса** — если одна и та же
  зависимость указана дважды в сигнатуре одного роута, она будет вызвана дважды (в настоящем
  FastAPI — один раз, результат переиспользуется). Об этом уже честно сказано ученику в
  `module9.js` (урок `dependency-injection`, callout "Честная разница..."). Если когда-нибудь
  понадобится это исправить — резолвер нужно переделать так, чтобы кэшировать по `id(dependency)`
  в рамках одного вызова `_call`.
- **Мини-SQLAlchemy (`miniSqlalchemy.py`) не поддерживает**: связи между таблицами
  (`relationship`/`ForeignKey` есть только как заглушка через тип столбца, JOIN не реализован),
  `filter()` с сравнениями (`>`, `<`, `LIKE`) — только `filter_by(**kwargs)` на точное равенство,
  сортировку (`order_by`), пагинацию на уровне ORM. Если модулю 10 (тестирование) или итоговым
  проектам понадобится что-то из этого в виде реально исполняемого кода — придётся расширять
  `miniSqlalchemy.py` по тому же принципу (посмотри на существующий `Query` класс).
- **passlib/bcrypt НЕ загружаются в Pyodide** (bcrypt — C-расширение, в дистрибутив Pyodide не
  входит, и подключать его через `micropip` не проверялось и не гарантированно сработает).
  Во всех уроках, где нужно реальное исполняемое хеширование паролей, используется
  `hashlib`+`secrets` (см. `module8.js`, урок `password-hashing`) — настоящий, честный, работающий
  код. `passlib`/`bcrypt` показываются только как "как это выглядело бы по-настоящему" текстом
  внутри `steps`, без `sandbox`. Не пытайся дать реально исполняемый пример на `passlib` без
  предварительной проверки через Node+Pyodide (см. рецепт валидации выше) — весьма вероятно,
  что он не загрузится.
- **`terminalSimulator.js` пока не знает команду `docker`** — понадобится для модуля 13,
  добавь обработку по образцу того, как там уже сделаны `pip`/`uvicorn`.
- **Сборка предупреждает про размер чанка** (`Some chunks are larger than 500 kB`) при
  `npm run build` — это ожидаемо (весь контент уроков идёт одним JS-бандлом) и не является
  ошибкой; можно будет решить позже через `dynamic import()` по модулям, если это когда-нибудь
  станет реальной проблемой производительности — не занимайся этим сейчас без явного запроса.
- Никакого автотеста на сам контент уроков нет — единственный способ проверки песочниц —
  ручной прогон через Node+Pyodide, описанный выше. Не пропускай этот шаг.
